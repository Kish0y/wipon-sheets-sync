# Синхронизация продаж Wipon (Prosklad) → Google Таблица

Скрипт забирает продажи из кассовой системы Wipon и дописывает их в Google Таблицу.
Одна строка таблицы — один проданный товар:

| Дата и время продажи | Филиал | Название товара | Количество | Цена за единицу | Сумма | ID продажи |
|---|---|---|---|---|---|---|

Рядом ведётся второй лист — **«Сводка»**, где итоги разложены по филиалам.

Скрипт рассчитан на запуск по расписанию (например, раз в 5 минут): он отрабатывает
один раз и завершается. Бесконечных циклов внутри нет.

## Установка

### 1. Зависимости

```bash
python -m venv .venv
```

Активируем окружение — Windows (PowerShell):

```bash
.venv\Scripts\Activate.ps1
```

Linux / macOS:

```bash
source .venv/bin/activate
```

Ставим библиотеки:

```bash
pip install -r requirements.txt
```

### 2. Google: сервисный аккаунт и доступ к таблице

1. Зайти в [Google Cloud Console](https://console.cloud.google.com/), создать проект.
2. Включить **Google Sheets API** (APIs & Services → Library → Google Sheets API → Enable).
3. Создать сервисный аккаунт: IAM & Admin → Service Accounts → Create.
4. У созданного аккаунта: Keys → Add key → Create new key → **JSON**. Скачается файл с ключом.
5. Положить этот файл в папку проекта под именем `service_account.json`
   (или указать другой путь в `.env`, переменная `GOOGLE_CREDENTIALS_FILE`).
6. Открыть JSON-ключ и скопировать оттуда значение поля `client_email`
   (вида `имя@проект.iam.gserviceaccount.com`).
7. Открыть Google Таблицу → «Настройки доступа» → добавить этот email с ролью **Редактор**.
   Без этого шага скрипт получит ошибку доступа: сервисный аккаунт — это отдельный
   «пользователь», и таблицу ему нужно расшарить.

### 3. Файл `.env`

Скопировать образец и заполнить своими значениями:

```bash
copy env.example .env
```

Минимум, что нужно заполнить:

```
WIPON_USERNAME=77000000000
WIPON_PASSWORD=пароль_от_кассы
WIPON_EMPLOYEE_ID=1
GOOGLE_SPREADSHEET_ID=1AbC...   # из ссылки на таблицу, между /d/ и /edit
GOOGLE_CREDENTIALS_FILE=service_account.json
```

`GOOGLE_SPREADSHEET_ID` берётся из адресной строки:
`https://docs.google.com/spreadsheets/d/`**`ВОТ_ЭТОТ_КУСОК`**`/edit`

Остальные параметры (часовой пояс, глубина первой выборки, размер страницы и т. д.)
описаны комментариями прямо в `env.example`.

## Запуск

### Сначала — проверка на фейковых данных

Ничего никуда не пишет, просто показывает, какие строки получились бы:

```bash
python wipon_sync.py --test --dry-run
```

Пишет фейковые продажи в настоящую таблицу — так проверяется доступ к Google:

```bash
python wipon_sync.py --test
```

Запустите вторую команду дважды подряд. Второй запуск ничего не добавит и напишет
в лог, что все продажи уже записаны — так работает защита от дублей.
Тестовые строки потом можно просто удалить из таблицы вручную (их ID начинаются с `TEST-`).

### Боевой запуск

```bash
python wipon_sync.py
```

### Все флаги

| Флаг | Что делает |
|---|---|
| `--test` | Фейковые данные вместо API Wipon |
| `--fake-count N` | Сколько фейковых чеков создать (по умолчанию 4) |
| `--dry-run` | Показать строки в консоли, ничего не записывать |
| `--days N` | Разово забрать продажи за последние N дней |
| `--reset-state` | Забыть, что уже синхронизировано (удаляет `state.json`) |
| `--refresh-items` | Перезагрузить справочник товаров, не глядя в кеш |
| `--verbose` | Подробный лог (уровень DEBUG) |

Коды возврата: `0` — успех, `1` — ошибка выполнения (сеть, API, таблица),
`2` — ошибка настройки (не заполнен `.env`, не найден JSON-ключ).

## Филиалы, фильтр товаров и сводка

### Филиалы

В кассе Wipon несколько торговых точек, и каждая продажа приносит свою:
филиал лежит в объекте `stock` (в терминах API это «склад»), поле `stock.name`.
Скрипт кладёт его в колонку «Филиал», отдельных запросов для этого не нужно.

### Фильтр товаров

Иногда нужно следить не за всем ассортиментом, а за парой позиций. За это отвечает
переменная `ITEM_FILTER` в `.env`:

```
ITEM_FILTER=Магний 3x Nurelum
```

Несколько товаров перечисляются через точку с запятой:

```
ITEM_FILTER=Магний 3x Nurelum;Омега 1000 мг 100 капсул
```

Пустое значение означает «писать все товары»:

```
ITEM_FILTER=
```

Названия сравниваются без учёта регистра и лишних пробелов, но в остальном должны
совпадать с тем, как товар назван в кассе. Посмотреть точное написание можно
в `raw_sale_sample.json` (поле `item.title`).

**Важно:** фильтр действует на момент записи. Товары, отсеянные раньше, задним числом
в таблице не появятся — если фильтр расширить, старые продажи по новому товару
придётся долить вручную: `python wipon_sync.py --reset-state --days 30`
(лист перед этим лучше очистить, иначе прежние строки останутся).

Если скрипт крутится на GitHub Actions, фильтр меняется не в `.env`, а в файле
`.github/workflows/sync.yml`, в блоке `env` шага «Синхронизировать продажи».

### Лист «Сводка»

Пересчитывается при каждом запуске по данным самого листа продаж, поэтому показывает
всё накопленное, а не только последнюю порцию:

```
Сводка по товару:  Магний 3x Nurelum
Обновлено:         03.09.2026 00:32

Основной склад
  Количество, шт     88
  Сумма, тг      991 200
  Чеков               62

2 точка
  Количество, шт     27
  ...

ИТОГО ПО ВСЕМ ФИЛИАЛАМ
  Количество, шт    133
```

Порядок филиалов постоянный и не зависит от того, где больше продали, — иначе строки
прыгали бы от запуска к запуску. Сортировка «естественная» (функция `branch_sort_key`
в `transform.py`): сначала филиалы без номера в названии, затем по возрастанию номера.

```
Основной склад → Склад на Абая → 2 точка → 3 точка → 10 точка
```

Обычная сортировка по алфавиту поставила бы «2 точка» впереди «Основного склада»,
потому что цифры идут раньше букв.

«Чеков» считается по уникальным ID продаж: в одном чеке товар может встретиться
несколькими строками, но чек это один.

Лист каждый раз переписывается целиком. Если сводка почему-то не обновилась, запуск
не падает — продажи важнее витрины, в лог попадёт предупреждение.

## Автозапуск через GitHub Actions (бесплатно, без сервера)

Самый простой способ добиться работы без включённого компьютера: GitHub
запускает скрипт по расписанию на своих машинах. Настройка — в файле
`.github/workflows/sync.yml`.

### 1. Загрузить проект на GitHub

```bash
git remote add origin https://github.com/ВАШ_ЛОГИН/wipon-sheets-sync.git
git push -u origin main
```

Файлы `.env`, `service_account.json`, `token.json` в репозиторий **не попадают** —
они перечислены в `.gitignore`. Проверить это можно так:

```bash
git check-ignore .env service_account.json    # должны быть перечислены оба
```

### 2. Прописать секреты

Settings → Secrets and variables → Actions → New repository secret.
Нужны пять штук:

| Имя секрета | Что положить |
|---|---|
| `WIPON_USERNAME` | Номер телефона вида `77XXXXXXXXX` |
| `WIPON_PASSWORD` | Пароль от кассы |
| `WIPON_EMPLOYEE_ID` | ID сотрудника (`python whoami.py`) |
| `GOOGLE_SPREADSHEET_ID` | ID таблицы из ссылки |
| `GOOGLE_SERVICE_ACCOUNT_JSON` | **Всё содержимое** файла `service_account.json`, целиком |

### 3. Проверить

Вкладка Actions → «Синхронизация продаж Wipon» → **Run workflow**.
Запуск вручную не ждёт расписания и сразу покажет, всё ли настроено.

### Что нужно знать про этот способ

- **Расписание неточное.** Указано «каждые 10 минут», но GitHub при нагрузке
  задерживает запуск на 10–20 минут. Продажи не теряются, просто приходят позже.
- **Машина одноразовая:** `state.json` и `token.json` между запусками не сохраняются.
  Поэтому в workflow включён `RECONCILE_WITH_SHEET=1` — от дублей защищает сверка
  с колонкой «ID продажи» в самой таблице. Токен запрашивается заново каждый раз.
- **Расписание отключается при простое.** Если в репозиторий 60 дней не делать
  коммитов, GitHub выключит cron и пришлёт письмо. Достаточно раз в пару месяцев
  сделать любой коммит либо нажать Run workflow вручную.
- Для публичного репозитория минуты не тарифицируются. Для приватного даётся
  2000 минут в месяц — при запуске каждые 10 минут этого не хватит,
  нужно ставить интервал 30 минут.

## Установка на сервер (Oracle Cloud Always Free)

Чтобы синхронизация работала круглосуточно, а не только при включённом компьютере.
Oracle даёт бесплатную виртуальную машину бессрочно, вместе с публичным IP.

### 1. Завести сервер

1. [oracle.com/cloud/free](https://www.oracle.com/cloud/free/) → Start for free.
2. При регистрации спросят **Home Region** — он выбирается **навсегда**, сменить нельзя.
   Ближайшие к Казахстану: **UAE (Dubai)**, дальше Германия (Frankfurt) или Индия (Mumbai).
3. Понадобится карта для проверки: спишут около $1 и вернут. Аккаунт остаётся
   на тарифе Always Free, автосписаний не будет, пока сам не нажмёшь Upgrade.
4. Создать машину: Compute → Instances → Create Instance.
   - Image: **Ubuntu 22.04** (или 24.04)
   - Shape: **VM.Standard.E2.1.Micro** (AMD, 1 ГБ RAM) — помечена «Always Free».
     ARM-машины (Ampere A1) мощнее, но их часто нет в наличии — для нашей задачи
     хватает микро-машины с огромным запасом.
   - SSH keys: **Save private key** — скачать файл `.key`, без него на сервер не зайти.
5. Записать **Public IP address** созданной машины.

### 2. Скопировать проект на сервер

С рабочего компьютера (замените `IP` на адрес машины, `key.key` — на скачанный ключ):

```bash
# Код проекта
scp -i key.key -r *.py requirements.txt deploy ubuntu@IP:/tmp/wipon/

# Секреты — отдельно, они не в репозитории
scp -i key.key .env service_account.json ubuntu@IP:/tmp/wipon/
```

### 3. Запустить установку

```bash
ssh -i key.key ubuntu@IP
sudo mkdir -p /opt/wipon-sync && sudo mv /tmp/wipon/* /opt/wipon-sync/
sudo bash /opt/wipon-sync/deploy/setup.sh
```

Скрипт поставит Python, зависимости, часовой пояс Asia/Almaty, сделает пробный
запуск и включит systemd-таймер на каждые 5 минут.

### 4. Проверить, что работает

```bash
systemctl list-timers wipon-sync.timer    # когда следующий запуск
journalctl -u wipon-sync.service -n 50    # что было в последних запусках
tail -f /opt/wipon-sync/sync.log          # лог самого скрипта
```

### Почему systemd-таймер, а не cron

- `Persistent=true` — если сервер был выключен, пропущенный запуск выполнится
  сразу после включения; cron бы его просто потерял.
- systemd не запустит вторую копию, пока работает первая.
- Логи собираются в `journalctl` вместе с кодами возврата.

## Как устроена защита от дублей

Работают два независимых механизма:

1. **`state.json`** — файл рядом со скриптом, в нём лежат ID уже записанных продаж
   и время последней успешной синхронизации. Состояние сохраняется **только после
   успешной записи** в таблицу: если Google или Wipon отвалились, следующий запуск
   заново возьмёт тот же период.
2. **Сверка с самой таблицей** — перед записью скрипт читает колонку F («ID продажи»)
   и выкидывает всё, что там уже есть. Это спасает, если `state.json` удалили или
   скрипт перенесли на другой компьютер. Отключается настройкой `RECONCILE_WITH_SHEET=0`.

Дополнительно каждый запуск берёт период с перекрытием в один день
(`SYNC_OVERLAP_DAYS`), потому что фильтры `date_from` / `date_to` в API работают
по датам. Лучше перечитать день и отбросить дубли по ID, чем потерять продажу.

## Как на самом деле устроен ответ API

В официальной документации примера ответа для списка продаж нет, поэтому структура
проверена на боевых данных. Вот что выяснилось (это уже учтено в коде):

```
GET /v1/employee/{employee_id}/sale
  id            — ID продажи (чека)
  created_at    — "2026-09-02 21:14:22", уже местное время, без часового пояса
  sum           — итог чека
  item_sale[]   — ПОЗИЦИИ ЧЕКА (именно item_sale, не items)
      quantity        — "1.000"
      selling_price   — цена за единицу УЖЕ СО СКИДКОЙ
      price           — цена до скидки
      item.title      — название товара
```

Два важных вывода:

1. **Название товара лежит прямо в ответе** (`item_sale[].item.title`), поэтому
   отдельный справочник товаров для заполнения таблицы не нужен — он подгружается
   только как запасной вариант, если у позиции вдруг не окажется вложенного `item`.
2. **Сумма = `quantity × selling_price`.** Проверено на чеке со скидкой: сумма всех
   строк чека в точности совпала с полем `sum` самой продажи. Брать `price` нельзя —
   это цена до скидки, итог получится завышенным.

При первом реальном запуске скрипт сохраняет сырой JSON первой продажи в файл
**`raw_sale_sample.json`** — если Wipon когда-нибудь переименует поля, сверяться нужно
с ним и править списки в начале `transform.py`.

### Формат колонок в таблице

Даты пишутся через `USER_ENTERED`, то есть Google сам распознаёт «02.09.2026 21:14:22»
как дату-время и хранит её числом (дней с 30.12.1899). Если у ячейки при этом числовой
формат, в таблице видно `46264,50641` вместо даты. Поэтому `sheets.py` явно объявляет:
колонка A — дата-время `dd.mm.yyyy hh:mm:ss`, колонка F (ID продажи) — текст, чтобы
длинные ID не превратились в `3,4379E+08`.

## Как узнать свой `employee_id` и правильный логин

Две вещи, на которых легко споткнуться:

**Логин — это номер телефона в формате `77XXXXXXXXX`**, начиная с семёрки, а не с восьмёрки.
Если написать `87761234567`, сервер ответит `404 Пользователь не найден`.

**`employee_id` — это НЕ ID пользователя.** У одного пользователя (владельца) есть
отдельная запись сотрудника со своим ID. Если перепутать, придёт ошибка
`403 У сотрудника нет нужного права или доступа к складу этой компании`.
Узнать правильный ID можно так — скрипт `whoami.py` покажет всех ваших сотрудников:

```bash
python whoami.py
```

Он делает `GET /v1/user` и печатает список из поля `employees`: нужный ID лежит там.

## Частые ошибки

| Что видно в логе | Что делать |
|---|---|
| `404 Пользователь не найден` | Логин должен начинаться с `7`, а не с `8`: `77761234567` |
| `403 У сотрудника нет нужного права или доступа к складу` | В `.env` указан ID пользователя вместо ID сотрудника — запустить `python whoami.py` |
| `Ошибка конфигурации: В .env не заданы...` | Заполнить `.env`, скопировав `env.example` |
| `Wipon вернул 401` | Проверить логин/пароль. Скрипт сам попробует получить новый токен один раз; если не помогло — удалить `token.json` |
| `Не удалось открыть таблицу ...` | Проверить `GOOGLE_SPREADSHEET_ID` и что таблица расшарена на `client_email` из JSON-ключа с ролью «Редактор» |
| `Часовой пояс не найден` | `pip install tzdata` |
| Фильтр по датам не работает | Поменять `WIPON_DATE_FORMAT` в `.env` на `%Y-%m-%d %H:%M:%S` |
| В таблице нет новых строк | Посмотреть `sync.log`: скорее всего продажи уже записаны и отсечены по ID |

## Что скрипт НЕ делает

- Не обрабатывает возвраты (`/v1/employee/{employee_id}/refund`) — при возврате
  строка продажи останется в таблице как есть.
- Не удаляет и не правит уже записанные строки, только дописывает новые.
- Не учитывает скидки на позицию (см. раздел про колонку «Сумма»).
